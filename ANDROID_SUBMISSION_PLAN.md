# APeX · Android Submission Plan

Status: **planning-only — no Android build has been produced yet.** The app has only ever shipped
for iOS (`eas build --platform ios --profile production`, see `APP_STORE_SUBMISSION_PLAN.md`).
This doc is the Android counterpart: what's already in place from sharing one React Native
codebase, what's genuinely missing, and the process/timeline items (Google Play's closed-testing
requirement in particular) that are easy to miss and gate the release by weeks if started late.
Same tagging convention as the iOS doc: ✅ **Done**, 🟡 **Partial / needs a decision**, 🔴 **Not
started** — keep tags current as items get done, don't just append prose under stale ones.

**The realistic timeline driver is §3.3**, not the code work: Google requires 12 opted-in testers
actually using the app for 14 *consecutive* days before a new personal developer account can
request production access. That clock doesn't start until you have a build in a closed track with
real testers opted in — so it's worth getting §1/§2 done and a build into closed testing as soon as
possible, even before the store listing/metadata is finished, rather than treating testing as the
last step.

## 0. Architecture — unchanged from iOS

Same backend, same Supabase project, same Python worker on your PC — Android is purely a second
client build against infrastructure that already exists and doesn't know or care which OS is
calling it. See `APP_STORE_SUBMISSION_PLAN.md` §0 for the diagram; nothing about it changes here.

## 1. Already in place (shared one-codebase wins)

Confirmed by reading the actual source, not assumed from "it's cross-platform so it should work":

- **`mobile/app.json`**: an `android` block already exists (`package: "com.apexathletics.app"`,
  matching the iOS `bundleIdentifier`) with `CAMERA`, `READ_EXTERNAL_STORAGE`,
  `MODIFY_AUDIO_SETTINGS`, `RECORD_AUDIO` permissions declared.
- **Push notifications**: `mobile/src/api/pushNotifications.ts` already creates the Android
  notification channel Android requires (`Notifications.setNotificationChannelAsync('default', ...)`)
  — the client-side half of Android push is done; only the Firebase/FCM credential setup (§2.3) is
  missing.
- **`content://` URIs**: `mobile/src/utils/video.ts`'s `normalizeVideoUri()` already copies an
  Android `content://` URI (what `expo-image-picker` can return there, unlike iOS's `file://`) to a
  real cache file before it's used — called from `CameraScreen.tsx` on every confirmed video,
  recorded or picked from the library. This is exactly the kind of silent Android-only failure mode
  that's easy to miss; it's already handled.
- **Font-rendering quirks**: `IndividualRoutineScreen.tsx` and `VideoPlayer.native.tsx` already
  apply `includeFontPadding: false` / explicit `textAlignVertical` — Android-only text-metric fixes
  that prevent visual misalignment Android would otherwise have and iOS wouldn't.
- **Target API level**: `mobile/package.json` pins `"expo": "~54.0.36"`. Expo SDK 54 targets
  Android 16 (API 36) by default — already ahead of both Play's current requirement (API 35, in
  effect since Aug 2025) and the incoming one (API 36, required for new apps from Aug 31 2026). No
  action needed here; worth a quick confirmation in the first build's logs, not a real risk.
- **Platform-split components** (`.native.tsx`/`.web.tsx` pairs — `LiveCamera`, `VideoPlayer`):
  split on native-vs-web, not iOS-vs-Android, so both phones already share one implementation. The
  live camera-recording path (`LiveCamera.native.tsx`, used by `CameraScreen.tsx`) has no
  Android-specific branch at all — worth extra attention in on-device testing (§4) for exactly that
  reason, since it hasn't needed one yet doesn't mean it won't.
- **Not a real risk — dead code**: `PoseView.native.tsx` (and its only consumers,
  `AssessmentPanel`/`PhysioCard`/`PhysioDemo`, all reachable only through the retired
  `AnalysisScreen.tsx`) contains WebView workarounds explicitly commented "required on iOS" with no
  Android branch. This looked concerning at first pass, but `AnalysisScreen.tsx` is never imported
  from `App.tsx` — confirmed unreachable in the shipped app (same on iOS today). Don't spend testing
  time here.

## 2. Cleanup before the first Android build

### 2.1 Stale `RECORD_AUDIO` permission — 🟡

`app.json`'s Android `permissions` array still lists `RECORD_AUDIO`, but audio recording is
disabled elsewhere in the same file (`expo-camera` plugin's `"recordAudioAndroid": false`,
`expo-av`'s `microphonePermission: false`, `plugins/withoutRecordAudio.js`) — this mirrors a
deliberate iOS mic-permission removal (commit `0a333b3`) that wasn't mirrored into the Android
permissions list. Leaving it in means Google Play's Data safety/permissions review sees a sensitive
permission (microphone) declared with nothing in the app that justifies it. Remove `RECORD_AUDIO`
(and `MODIFY_AUDIO_SETTINGS`, if nothing else needs it) from `app.json`'s `android.permissions`.

### 2.2 Adaptive icon — 🔴

`mobile/assets` only has a flat `icon.png` (the iOS-style square icon) — no adaptive-icon
foreground/background image, and `app.json`'s `android` block has no `adaptiveIcon` key at all.
Without one, Android falls back to the flat icon, which typically renders with an unwanted white
box/no mask on modern launchers instead of the circle/squircle/etc. shape the user's launcher
expects. Not a functional bug, but a visible, immediately-obvious "this wasn't really made for
Android" tell — worth fixing given the goal is parity. Needs: a foreground image (subject on a
transparent background, safe-zone padding per Android's adaptive icon spec) + a background color or
image, added as:
```json
"android": {
  "adaptiveIcon": {
    "foregroundImage": "./assets/adaptive-icon-foreground.png",
    "backgroundColor": "#07101C"
  }
}
```
(`#07101C` is the app's own `colors.bg` from `mobile/src/theme.ts` — keeps it consistent with the
existing dark navy identity rather than picking an arbitrary background.)

### 2.3 Firebase / FCM setup for push notifications — 🟡

This is the one genuinely functional (not cosmetic) cross-platform gap found. Expo's push service no longer
proxies Android push through a shared credential — as of the current FCM v1 API, **each app needs
its own Firebase project**. Two separate pieces, easy to conflate:

1. A **Firebase project** for the app, with `google-services.json` downloaded from Firebase Console
   → Project settings → Your apps → Android app, referenced in `app.json`. ✅ **Done** — project
   `apex-2bc44` created, Android app registered under package `com.apexathletics.app`,
   `mobile/google-services.json` in place, `app.json`'s `android.googleServicesFile` points to it.
   Safe to commit — contains no secrets (a Firebase Android `api_key` is a public client
   identifier, not a credential, per Firebase's own docs).
2. A **separate FCM v1 service account key** (Firebase Console → Project settings → Service
   accounts → Generate new private key), uploaded to EAS via `eas credentials` (Android → Push
   Notifications: Manage your FCM V1 key). 🔴 **Still needed** — without this half, the
   `google-services.json` alone isn't enough for Expo's push service to actually send through FCM.

Without this, Android push notifications (manager "poke", "video ready", injury-status alerts —
everything `pushNotifications.ts` sends) will silently no-op on Android while continuing to work
fine on iOS — exactly the kind of platform difference the user asked to avoid, and one that's easy
not to notice until someone reports "I never got the notification."

### 2.4 `eas.json` Android profiles — 🔴

Currently `eas.json`'s `build.production` etc. have no `android: {...}` override — Android will
build off the same generic profile as iOS (fine as a starting point; EAS defaults Android
`production` builds to an `.aab`, which is what Play Store submission needs). `submit.production`
is empty — needs an `android` entry once the Play Console service account key (§3.1) exists:
```json
"submit": {
  "production": {
    "android": {
      "serviceAccountKeyPath": "./google-play-service-account.json",
      "track": "internal"
    }
  }
}
```
Start the `track` at `internal` (or the closed-testing track directly) rather than `production` —
matches the mandatory closed-testing flow in §3.3 anyway.

## 3. Google Play process (the part that isn't code)

### 3.1 Google Play Developer account + service account — 🔴

- Sign up at [play.google.com/console/signup](https://play.google.com/apps/publish/signup/)
  (one-time $25 fee) if you don't already have one, and create the app entry ("Create app") —
  needed before `eas submit` can target it.
- Create a Google Cloud service account for EAS to submit on your behalf (distinct from the FCM one
  in §2.3 — this one talks to the Play Developer API, not Firebase): Google Cloud Console → IAM &
  Admin → Service Accounts → Create → generate a JSON key → enable the **Google Play Android
  Developer API** for that project → in Play Console, Users and permissions → Invite the service
  account's email → grant "View app information," "Edit and delete draft apps," "Release to
  production and manage testing tracks," "Manage store presence." Upload the resulting JSON to EAS
  (`eas credentials` → Android → or via the eas.json path in §2.4).

### 3.2 First build + submit — 🟡 build done, submit still blocked on §3.1

`eas build --platform android --profile production` succeeded (build `6404b22a`) — EAS
auto-generated and now manages the upload keystore, and the app identifier `com.apexathletics.app`
is registered under Android credentials. Output is a **`.aab`** (Android App Bundle), which is
correct for the eventual Play Store upload but — unlike an `.ipa` or an Android `.apk` —
**cannot be installed directly on a device or emulator**; it only becomes runnable after Google
Play processes it (or via `bundletool`, not worth it here). `eas submit --platform android` is
still blocked on §3.1 (no Play Console app/service account yet).

**For on-device testing right now, before Play Console is set up**, build the `preview` profile
instead — `distribution: "internal"` in `eas.json` makes EAS produce an installable `.apk` with a
direct download link (same idea as an iOS ad-hoc build), no Play Console involved:
```
cd mobile
eas build --platform android --profile preview
```
Once §3.1 is done, `eas submit --platform android` picks up the existing production `.aab` (or
build a fresh one) and uploads it to the track configured in `eas.json` (§2.4). First submission
lands as a **draft** on the track until store-listing tasks are finished in Play Console — same
"draft" gate the iOS flow's App Store Connect has.

### 3.3 Closed testing — 🔴 (start this early — it's the actual bottleneck)

For a personal developer account created after Nov 13, 2023 (assume this applies unless you know
otherwise), Google requires **12 testers, opted in and actually using the app, for 14 consecutive
days**, before you can apply for production access. Adding 12 email addresses to a tester list does
*not* start the clock — each person has to accept the tester invite and open the app; the 14 days
resets if the count drops below 12 at any point. Practically: create a Closed testing track in Play
Console, add a tester list (a plain email list or a Google Group), share the opt-in link, and
recruit 12 real people (friends, teammates, beta athletes already using the iOS build) before/while
finishing the rest of this doc — not after.

### 3.4 Store listing — 🔴

- **Privacy policy**: already done — `https://danzlotnikov.github.io/APeX/privacy-policy.html`,
  same URL already linked from both Settings screens on iOS, reusable as-is for Play Console's
  privacy policy field.
- **Data safety section**: a questionnaire in Play Console (App content → Data safety) declaring
  what the app collects/shares. Based on what's actually in this codebase: account email (auth),
  full name, height/weight/date of birth (`athlete_profiles`), exercise videos (uploaded to
  Supabase Storage), and an Expo push token — none of it sold or shared with third parties, video
  storage tied to the account and deletable via the existing account-deletion flow. Use that as the
  starting answer set rather than re-deriving it from scratch.
- **Content rating questionnaire**, **app category**, **screenshots** (Android requires
  phone-size screenshots separate from iOS's; existing App Store screenshots won't satisfy this
  automatically), **short/full description** — all standard Play Console store-listing steps, not
  investigated further here since they're pure content, not code/config.

## 4. On-device parity testing — the part that actually answers "does it work the same"

Everything above gets a build into Google's hands; none of it *proves* parity. Before calling
Android done, actually run the app on a real Android device (or a Play-Store-track install once
§3.3 is underway) and walk through, side-by-side with the iOS build:

- **Record a video** (the core flow) — camera permissions prompt correctly, recording, preview,
  confirm/upload. This is the path with the most native-module surface area (`expo-camera`,
  `expo-file-system`) and the least amount of explicit Android testing to date.
- **Pick a video from the library** instead of recording — exercises the `content://` → `file://`
  normalization in §1 specifically.
- **Push notifications** end-to-end (poke, video-ready, injury status) — will only be meaningful
  once §2.3 is done; this is the one item likely to be silently broken without it.
- **Sign-up flow**, including the new sport-picker step (`SignUpScreen.tsx`) — newest screen in the
  app, not yet run on Android at all.
- **Manager flows** (athlete list, per-athlete profile, routine editing) — mostly plain RN
  components/ScrollViews, lowest platform risk, but worth a pass.
- **Visual pass**: dark theme rendering, safe-area insets on a phone with gesture nav vs a
  notch/punch-hole layout, and the adaptive icon (§2.2) actually looking right on the home screen.

Log anything found here back into this doc under a new "§5 Known Android bugs" section as it comes
up, same as the iOS plan tracks its own findings — don't let this list live only in chat history.
